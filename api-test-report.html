What was run

Three passes, all against a live database — not mocks.

The API was started on localhost:4000 against the Lightsail PostgreSQL instance. The database turned out to be empty scaffolding — schema present, zero rows in every table — so writes were safe and no production data was at risk.

Defects found

Ordered by severity. All eight are fixed and re-verified.

High

The admin audit trail recorded nothing at all

Fixed

The audit middleware wrote to a table named audit_log. That table does not exist — the audit table is activity_logs. Nor was it only the name: none of the eleven columns existed either (operation_id, method, path, status_code, ip_address, target_id, payload). 

relation "audit_log" does not exist

It went unnoticed because the write is deliberately fire-and-forget — an audit outage must not fail a refund that already succeeded. So every failure landed in a log line instead of a response, and every request carried on returning 200.

Impact: every admin mutation since the system was built — price changes, refunds, stock adjustments, role grants — appeared to be audited and was not. There was no trail.

Rewritten against the real activity_logs columns. action carries the operationId, which is unique across both surfaces, so method and path are recoverable from it. Verified writing correctly after the fix.

High

Arrays bound as row constructors broke the public catalogue

Fixed

Drizzle expands a JavaScript array inside a sql template as a comma-separated tuple. So ANY(${kinds}) compiled to a row constructor, which PostgreSQL will not compare against text: 

AND c.kind = ANY(($1, $2))
params: occasion, festival, recipient
Impact: GET /v1/products returned 500, and 54 further public catalogue, collection and content endpoints failed or hung. This is the storefront's entire product listing.

Four sites across three modules — catalogue (×2), search and content. Fixed with sql.param() plus an explicit ::text[] / ::uuid[] cast, which binds the whole array as one parameter.

High

Five inventory reports queried columns that do not exist

Fixed 
column pv.title does not exist

The reports selected COALESCE(pv.title, hi.title, pm.name). Neither product_variants.title nor hamper_items.title is a real column — a variant's display name lives on products.title plus the variant's option_label, and a hamper item has name.

Impact: inventory-aging, dead-stock, inventory-valuation, stock-velocity and purchase-forecast all returned 500 — five of the ten reports.

Three query sites corrected, with the missing products join added to each.

High

Ambiguous column reference broke the admin order list

Fixed 
column reference "id" is ambiguous

Selecting a whole table makes Drizzle emit its columns unqualified, and it then renders ${orders.id} unqualified inside the correlated subqueries too. In the subquery that joins shipments to couriers, a bare id matches both tables and PostgreSQL refuses the entire statement.

Impact: GET /v1/admin/orders and the order detail endpoint both returned 500. The admin console could not list a single order.

Qualified as orders.id in all four subqueries — not only the one that broke. The other three have a single table each and got away with it, which is exactly why they were fixed too.

Medium

Audit rows could push a SKU into a UUID column

Fixed

The middleware took the first string path parameter it found and wrote it to entity_id, which is uuid. Routes keyed by SKU, handle or report name — /v1/admin/barcodes/:sku, /v1/admin/reports/:report/export — would have failed the insert once the table name was corrected. Now only a value matching the UUID shape is recorded, and null otherwise, which is the truthful answer.

Medium

Three migrations were never applied, and the runner could not apply them

Fixed

The schema had been deployed by running SQL directly, so schema_migrations was never created. The runner therefore started at 0001_initial.sql and failed on objects that already existed — meaning 0003, 0004 and 0005 could not be applied at all.

Impact: every Phase 4–7 endpoint — production, bulk orders, stock counts — would have 500'd against this database, because the tables did not exist.

Backfilled the tracking table after verifying each migration's objects were genuinely present, rather than assuming. All three then applied cleanly.

Medium

The whole authenticated API is unavailable when Redis is down

Confirmed by design

authenticate checks a Redis denylist on every request so that "sign out everywhere" takes effect immediately. With Redis unreachable that check throws and the request fails closed — all 203 admin routes returned 401.

That is the correct security posture and not a defect. It is recorded here because it is an operational fact worth knowing: Redis is a hard dependency for authentication, not a cache you can lose. Rate limiting, by contrast, deliberately fails open — so a Redis outage silently removes brute-force protection while keeping the API up.

Medium

A live Razorpay key sits in the working .env

Guard verified

RAZORPAY_KEY_ID is a rzp_live_… key. The application's own guard caught this correctly and refused to start in development, printing a clear refusal rather than charging a real card. That guard works and is worth keeping.

The key itself should still be rotated and replaced with a rzp_test_… key for local work — a live secret in a development .env is one careless NODE_ENV=production away from moving real money.

What this run could not cover

  • Business logic on real data. The database is empty, so list endpoints returned empty pages and detail endpoints returned 404. Routing, authentication, permissions, validation and error handling were all exercised; pricing, discounting and fulfilment arithmetic were not.
  • Rate limiting. No Redis was available locally, so a minimal stub stood in. It answers the denylist correctly but does not implement the limiter's Lua scripts, so limits were not measured.
  • Payments. Razorpay was never called — deliberately. The keys in .env are live.
  • Firebase sign-in. POST /v1/auth/firebase needs a real Firebase ID token minted by a browser completing an SMS challenge. Its decision logic is covered by 74 unit tests instead.
Cleanup. The temporary Super Admin created for pass 3 has been deleted along with its sessions — it had a known password on the shared instance. Its audit rows were deliberately kept: actor_staff_id is ON DELETE SET NULL, so the trail survives with a null actor. Deleting evidence to tidy up would be the wrong instinct for an audit table. All harness scripts and the Redis stub were removed.
